Listing document (what's in OpenSearch / the seed data):
{
  "id": "string (uuid)",
  "name": "string",
  "category": "pg | mess | tiffin | print_shop | atm | other",
  "description": "string",
  "location": { "lat": number, "lon": number },
  "address": "string",
  "price": number | null,
  "price_unit": "per_meal | per_page | per_month | per_copy | null",
  "hours": [ { "day": "mon|tue|wed|thu|fri|sat|sun", "open": "HH:MM", "close": "HH:MM" } ],
  "phone": "string | null",
  "tags": ["string"],
  "rating": number | null
}
(empty "hours" array means 24x7 / unknown — treat as always open)

POST /parse   (Person 2 builds this)
  Request:  { "query": "any tiffin service open right now that's cheap" }
  Response: {
    "category": "pg | mess | tiffin | print_shop | atm | other | null",
    "radius_km": number,           // default 2 if user didn't mention distance
    "open_now": boolean,           // true if query implies "now" / "currently open"
    "sort_by": "cheapest | nearest | rating | null",
    "max_price": number | null,
    "keywords": ["string"]         // leftover descriptive terms for fuzzy text match
  }
  Note: /parse never returns lat/lon — it can't know the user's real position
  from text alone. The frontend supplies user_location separately to /search.

POST /search   (Person 3 builds this)
  Request:  {
    "category": "tiffin" | null,
    "radius_km": 2,
    "open_now": true,
    "sort_by": "cheapest",
    "max_price": 100,
    "keywords": ["cheap tiffin"],
    "user_location": { "lat": 12.9716, "lon": 77.5946 }   // required, from frontend
  }
  Response: {
    "results": [
      {
        "id": "string", "name": "string", "category": "tiffin",
        "distance_km": 0.4, "price": 60, "price_unit": "per_meal",
        "is_open_now": true, "address": "string",
        "location": { "lat": 12.97, "lon": 77.59 },
        "phone": "string | null", "tags": ["veg"], "rating": 4.2
      }
    ],
    "total": 1
  }

Frontend flow: user types a query -> POST /parse -> take the filters,
attach user_location (from browser geolocation, fallback to a campus
default constant) -> POST /search -> render list + map.

Contract you must implement:
  Input (from the API Gateway event body): { "query": "<free text>" }
  Output (JSON body, status 200): {
    "category": "pg | mess | tiffin | print_shop | atm | other | null",
    "radius_km": number,        // default 2 if the query doesn't mention distance
    "open_now": boolean,        // true if query implies "now"/"currently open"/"right now"
    "sort_by": "cheapest | nearest | rating | null",
    "max_price": number | null, // e.g. "under 50 rupees" -> 50
    "keywords": ["string"]      // leftover descriptive terms for fuzzy text search

  alone; the frontend attaches user_location separately later.

open" -> open_now:true; "cheap"/"cheapest"/"budget"/"under ₹X" ->
sort_by:"cheapest" and/or max_price:X; "near"/"nearby"/"within Xkm" ->
radius_km:X; "best"/"top rated" -> sort_by:"rating". Category words map to
the enum (e.g. "tiffin"/"mess"/"food" -> tiffin or mess, "PG"/"hostel" ->
pg, "print"/"xerox"/"photocopy" -> print_shop, "ATM"/"cash" -> atm).

PROMPT 3 — SEARCH SERVICE  (owns backend/search/)
================================================================================
You're building the OpenSearch-backed search Lambda for "Aas-Paas", a
campus essentials search app, for the AWS "First Commit" hackathon. It
takes structured filters (already parsed from natural language by a
teammate's Lambda) plus the user's coordinates, and returns ranked nearby
listings. Three teammates are building the infra skeleton, the NL query
parser, and the frontend in parallel against a frozen contract.

Work only inside backend/search/. Branch: feature/search. Person 1 is
setting up backend/infra/template.yaml which routes POST /search to
backend/search/app.py with handler `lambda_handler(event, context)`, and
passes the OpenSearch domain endpoint in as the env var
OPENSEARCH_ENDPOINT — keep that file path/handler name/env var name
exactly as given. There will initially be a placeholder file there from
Person 1 that you overwrite with real logic.

Contract you must implement:
  Input (JSON body): {
    "category": "tiffin" | null, "radius_km": 2, "open_now": true,
    "sort_by": "cheapest | nearest | rating | null", "max_price": number | null,
    "keywords": ["string"],
    "user_location": { "lat": number, "lon": number }   // always present
  }
  Output (JSON body, status 200): {
    "results": [ {
      "id": "string", "name": "string", "category": "string",
      "distance_km": number, "price": number | null,
      "price_unit": "string | null", "is_open_now": boolean,
      "address": "string", "location": { "lat": number, "lon": number },
      "phone": "string | null", "tags": ["string"], "rating": number | null
    } ], "total": number
  }

Listing documents in OpenSearch look like this (this is what you're
querying against — indexed by Person 1's seed script):
{
  "id": "string", "name": "string",
  "category": "pg | mess | tiffin | print_shop | atm | other",
  "description": "string", "location": { "lat": number, "lon": number },
  "address": "string", "price": number | null,
  "price_unit": "per_meal | per_page | per_month | per_copy | null",
  "hours": [ { "day": "mon..sun", "open": "HH:MM", "close": "HH:MM" } ],
  "phone": "string | null", "tags": ["string"], "rating": number | null
}
(empty "hours" array = always open)

Implementation notes:
- Query OpenSearch with a geo_distance filter (radius_km around
  user_location) + a term filter on category if present + a multi_match
  fuzzy query on keywords across name/description/tags.
- Given the dataset is tiny (30-50 listings), it's fine — and simpler — to
  compute `is_open_now` by comparing each candidate's `hours` against the
  current time in Python AFTER OpenSearch returns candidates, rather than
  writing an OpenSearch painless script. Filter to only is_open_now==true
  results when the request's open_now is true.
- Compute distance_km via OpenSearch's geo distance (or haversine in
  Python) between user_location and each listing's location.
- Sort by: price ascending if sort_by=="cheapest", distance_km ascending
  if sort_by=="nearest" or null (default), rating descending if
  sort_by=="rating". Apply max_price as a filter when present.

Deliverables:
1. backend/search/app.py with `lambda_handler(event, context)`, connecting
   to OpenSearch via the OPENSEARCH_ENDPOINT env var.
2. backend/search/requirements.txt (opensearch-py or similar).
3. backend/search/test_events/*.json — at least 5 sample API Gateway event
   JSON files with different filter combos, for `sam local invoke
   SearchFunction -e backend/search/test_events/sample1.json`.

You depend on Person 1's OpenSearch domain existing and being seeded to
test end-to-end — until that's ready, write your query-building logic
against a small hardcoded local list of 3-4 fake listings so you're not
blocked, then swap to the real OpenSearch client once Person 1 shares the
deployed OPENSEARCH_ENDPOINT.

Definition of done: each test event, run through `sam local invoke`,
produces output matching the contract shape with correct filtering/sorting
logic. Push to feature/search and open a PR.
